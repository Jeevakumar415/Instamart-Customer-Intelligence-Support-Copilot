# InstaMart – Customer Intelligence & Support Copilot

An AI-powered customer intelligence and support automation capstone project that combines customer analytics, churn prediction, support ticket triage, policy-based retrieval, and a safety-controlled refund agent.

## 1. Overview

### Project Description

InstaMart – Customer Intelligence & Support Copilot is an educational, end-to-end data analytics and AI project designed to demonstrate how customer data can support business intelligence and customer service operations.

The system integrates data engineering, customer segmentation, machine learning, natural language processing, retrieval-augmented generation (RAG), and controlled agent workflows.

It is organized into four major parts:

- **Part A – Data Foundation:** Data generation, cleaning, validation, SQLite database construction, SQL analysis, and exploratory data analysis.
- **Part B – Customer Intelligence:** RFM-based customer segmentation and machine-learning-based customer lapse prediction.
- **Part C – Support Ticket Triage:** Ticket classification, PII redaction, input guardrails, bounded retries, and deterministic fallback.
- **Part D – Policy RAG and Refund Agent:** Policy retrieval, grounded responses, refund-rule evaluation, safety controls, fallback handling, and checkpoint/resume demonstrations.

### Key Features

- Customer and order data processing.
- Customer segmentation using RFM analysis and K-means clustering.
- PCA-based customer segmentation analysis.
- Customer lapse prediction using Logistic Regression and Random Forest.
- Model evaluation using stratified data splitting and training-only cross-validation.
- Support ticket classification and prioritization.
- Regex-based PII redaction.
- Offline mock LLM integration.
- TF-IDF and cosine-similarity-based policy retrieval.
- Refund eligibility and safety-rule demonstrations.
- Bounded agent execution, fallback handling, and checkpoint/resume.

2. Clean, validate, and store structured data.

## 2. Reproduce

### Prerequisites

- Python 3.11 or newer.
- SQLite 3.25 or newer.
- Git.
- Visual Studio Code or another Python-compatible IDE.

### Installation

Clone the repository:

```bash
git clone https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git
cd YOUR-REPOSITORY
```

Create a virtual environment:

```bash
python -m venv .venv
```

Activate it on Windows:

```bash
.venv\Scripts\activate
```

Install the required dependencies:

```bash
pip install -r requirements.txt
```

### Execution Workflow

The project is organized into separate Python modules.

The general data preparation sequence is:

```bash
python generate_data.py
python clean_data.py
python audit_data.py
```

Database construction and analysis:

```bash
python build_database.py
python run_sql_queries.py
python eda_analysis.py
```

Part A validation:

```bash
python validate_part_a.py
```

Part B includes customer segmentation, lapse-model training, and a separate finalization workflow. Its corrected execution uses an isolated input bundle, run-specific output directory, provenance validation, and a separate finalization step.

Part C:

```bash
python part_c_ticket_triage.py
```

Part D includes the policy RAG and refund-agent modules:

```bash
python part_d_rag.py
python part_d_refund_agent_corrected.py
```

**Important execution notes:**

- Run workflows in their intended sequence and consult the corresponding module configuration and documentation.
- Database construction can rebuild the local database. Preserve existing database and historical evidence before executing it.
- Part B requires the configured input bundle and a separate training/finalization workflow. Do not treat the saved model as a substitute for the complete training process.
- The supplied `mock_llm.py` provides offline mock-model behavior. No paid LLM API or API key is required.
- Runtime outputs and checkpoints are generated by their respective workflows.

### D2 – Safe Refund Agent

The refund agent demonstrates rule-based refund eligibility evaluation and safety-controlled tool execution.

The documented policy rules include:

- Only completed orders are eligible for refund evaluation.
- Cancelled orders are not refundable.
- The delivery-duration condition requires more than 45 minutes.
- Refund amount is based on the full order amount.
- Amounts above ₹1,000 require support-lead approval.
- Approved refunds are described as returning to the original payment method within five working days.
- A seven-day request deadline is specified in the policy, but verified delivery timestamps are unavailable to establish compliance with this condition.

**Safety limitations:**

- The current implementation fails closed when required evidence is unavailable.
- It does not execute real payments or transfer money.
- It does not record new operational refunds in a live financial ledger.
- It does not provide an actual human approval queue.
- Human escalation wording in the mock workflow is simulated.
- Exactly-once execution across arbitrary process crashes is not guaranteed.

Historical simulated refund records are preserved as historical evidence and should not be interpreted as actual payments.

## 7. Limitations and Next Steps

Project Limitations

The project uses synthetic educational data and offline mock LLM integration.

The machine-learning models have not been established as production-ready.

Regex-based PII redaction is not comprehensive.

The RAG evaluation is limited to a small policy dataset and evaluation set.

The refund agent is a safety-controlled demonstration and does not process real refunds.

The project does not implement an operational human approval queue.

The seven-day refund deadline cannot be verified without reliable delivery timestamps.

The retention list is illustrative and is not a production customer-targeting list.

The D8 recovery demonstration does not establish exactly-once execution across arbitrary crashes.

Exact dependency and environment reproducibility is limited by the absence of pinned dependency versions.
